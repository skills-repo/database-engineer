# 恢复演练 Runbook 模板

> 配套 `references/backup-recovery.md`。**没演练过的备份不算备份**——这份模板的目的，
> 是把"我们有备份"这句话变成一个有日期、有耗时、有签字的记录。
>
> 用法：复制一份到你们自己的文档库，填空后按季度执行。历史记录不要删，
> 耗时的变化趋势本身就是容量预警信号。

## 演练前置检查（Day -1）

- [ ] 已申请**独立的恢复目标机**，确认**不是生产实例**（写错目标是本演练最大的风险）
- [ ] 目标机磁盘空间 ≥ 备份解压后体积 × 1.5
- [ ] 目标机的数据库大版本与生产一致（跨版本恢复是另一个课题，不要混在一起演练）
- [ ] 已通知相关方演练时间窗口，避免与其他变更撞车
- [ ] 准备好数据校验口径（见下方"第 4 步"），不要等恢复完了才想怎么验

## 演练步骤

### 1. 取备份（记录开始时间 ______）

```bash
# 从对象存储/备份机拉取，记录传输耗时——它常常是 RTO 里最大的一块
time aws s3 cp s3://<bucket>/<path>/full-YYYYMMDD.tar.gz /restore/
# 校验完整性（备份文件损坏往往到这一步才暴露）
sha256sum -c full-YYYYMMDD.tar.gz.sha256
```

> 记录：下载耗时 ______，校验结果 ______

### 2. 恢复全量（记录开始时间 ______）

```bash
# --- PostgreSQL 物理备份 ---
tar -xzf full-YYYYMMDD.tar.gz -C /var/lib/postgresql/data
# --- MySQL 物理备份（xtrabackup）---
xtrabackup --prepare --target-dir=/restore/full
xtrabackup --copy-back --target-dir=/restore/full
chown -R mysql:mysql /var/lib/mysql
```

> 记录：全量恢复耗时 ______

### 3. 重放增量到目标时间点（记录开始时间 ______）

```bash
# --- PostgreSQL PITR ---
# 在数据目录创建 recovery.signal，并在 postgresql.conf 配置：
#   restore_command = 'cp /archive/%f %p'
#   recovery_target_time = '2026-08-06 09:15:00'
#   recovery_target_action = 'promote'

# --- MySQL PITR ---
mysqlbinlog --start-datetime="2026-08-06 02:00:00" \
            --stop-datetime="2026-08-06 09:15:00" \
            /backup/binlog/mysql-bin.* | mysql -u root -p
```

> 记录：增量重放耗时 ______，重放的 binlog/WAL 段数 ______

### 4. 数据校验（这一步最容易被省略，也最不该省）

至少验三层，只验"能启动"是不够的：

```sql
-- a) 行数级：核心表与生产同一时点对账
SELECT COUNT(*) FROM orders WHERE created_at < '2026-08-06 09:15:00';

-- b) 校验和级：抽样字段做聚合，能发现行数对但内容错的情况
SELECT COUNT(*), SUM(amount), MAX(updated_at) FROM payments
WHERE created_at BETWEEN '2026-08-01' AND '2026-08-06';

-- c) 业务级：挑 3~5 条已知业务记录人工核对（例如某个真实订单的完整链路）
```

- [ ] 行数一致
- [ ] 聚合校验和一致
- [ ] 业务抽样一致
- [ ] 外键/约束未出现失效（PG：`SELECT * FROM pg_constraint WHERE NOT convalidated;`）

> 记录：不一致项 ______

### 5. 收尾

- [ ] **销毁恢复实例**（含磁盘），避免留下一份权限失控的生产数据副本
- [ ] 清理临时凭证
- [ ] 归档本次记录

## 复盘（必填，哪怕演练通过）

| 问题 | 影响 | 改进项 | 负责人 | 期限 |
|------|------|--------|--------|------|
| 例：下载备份耗时 38min，占 RTO 的 63% | RTO 逼近上限 | 在同 region 保留一份热备份 | | |
| | | | | |

**判定标准**：实测 RTO > 目标 RTO，或任一数据校验不通过 → 本次演练**不通过**，
必须在两周内完成改进并重测。不要把"基本恢复出来了"记为通过。

## 常见失败模式（来自真实事故，供对照自查）

1. **备份任务成功、内容为空**——脚本 `mysqldump` 报错但退出码被 `|| true` 吞掉。
   对策：校验备份文件大小与上次的偏差，超过 ±30% 直接告警。
2. **binlog/WAL 归档保留期短于全量备份周期**——全量在周日，归档只留 3 天，
   周五想恢复到周四某点却缺段。对策：归档保留期 ≥ 全量周期 × 2。
3. **恢复时才发现没有解密密钥**——备份加密了，密钥只在离职同事的机器上。
   对策：把"取密钥"作为演练的第 0 步，用真实流程取，不走后门。
4. **只演练了单表恢复，没演练过整库**——真出事时是整库。对策：至少一年一次整库演练。
5. **恢复目标机配置远好于/差于生产**——测出来的 RTO 没有参考价值。对策：同规格。
